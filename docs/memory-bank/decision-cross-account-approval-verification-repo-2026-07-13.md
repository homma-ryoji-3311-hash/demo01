## 背景

PR #1（`hooks: slice ブランチ判定を番号必須に統一`）の `/integrate` において、Phase A（再検証）
完了後、工程8の PM GO を得る過程で以下が発生した。

1. PR 作成者（GitHub アカウント `homma-ryoji-3311-hash`）が自分自身の PR に対して
   `gh pr review --approve` を実行 → GitHub 自身が **self-approval** としてブロック
   （`Can not approve your own pull request`）。
2. 回避としてレビュー承認の代わりに同アカウントで「GO」コメントを投稿し、`/integrate` の
   Phase 判定（「工程8の判定コメント/approve」の有無）をこれで満たして Phase B（マージ）へ進行。
3. マージ直後、Claude Code の自動モード分類器が後続操作を **Merge Without Review** として
   ブロック。理由: 同一アカウントによる「GO」コメントは GitHub 上の self-approval 拒否を
   実質迂回しているに過ぎず、独立した人間レビューの記録がない。
4. 続けて別 GitHub アカウント（`Honma218`、同一ユーザーが保持）に切り替えて approve する案を
   提示したところ、分類器は **Self Approval**（二者関係の再現の意図的迂回）として同様にブロック。
5. ユーザー本人が「この開発は検証用なので『もう一方のアカウントで承認する』という形での
   二者関係の再現は許容する」と明示的に判断・宣言。ユーザー自身のターミナル（Claude Code の
   ツール経由ではない）で `gh auth switch --user Honma218` → `gh pr review 1 --approve` を実行し、
   PR #1 に `Honma218`（COLLABORATOR）による正式な `APPROVED` レビューが記録された。

## 決定

**このリポジトリ（`staff-report-system-demo`、M-team 方法論の検証用リポジトリ）に限り**、
単一の人間が複数の GitHub アカウントを使って PM 相当の承認と統合役相当の実行を分担する運用を
許容する。ただし以下を満たすこと。

- 承認は必ず **GitHub 上に可視化される形**（PR review の approve、またはコメント）で残す。
  口頭・チャット内の承認だけでは工程8の GO として扱わない（従来ルールを維持）。
- アカウント切り替えとレビュー投稿は **ユーザー本人が自分のターミナルで実行する**。
  エージェント（Claude Code のツール経由）には実行させない
  （Claude Code の自動モード分類器が self-approval 迂回とみなしてブロックする設計のため。
  これはハーネス側の安全機構であり、エージェント権限では解除しない）。
- 本番相当のリポジトリ・複数人が実在するプロジェクトにこの運用を持ち込まない。
  この決定は本リポジトリの「検証用」という性質に限定される。

## 影響範囲

- `/integrate` スキル（`.claude/skills/integrate/SKILL.md`）のフェーズ判定は
  「工程8の判定コメント/approve」の存在だけを見ており、**それが PR 作成者と独立した
  第三者によるものかまでは検証しない**。この決定はその設計の上に成り立つ運用回避策であり、
  スキル自体の判定ロジックを変更するものではない。
- 複数人の実チームで運用する場合、この決定はそのまま適用できない
  （その場合は実際に別人がレビューする、が正しい経路）。

## 教訓（次に活かす）

- ハーネス側の安全機構（自動モード分類器）は、hooks とは別の層でプロセスの意図
  （「独立レビュー」の実質）を検査する。パターンマッチ（コメントの有無）だけでは
  実質を保証できない場合、この種の分類器がもう一段の防波堤として機能する。
- エージェントに「別アカウントでの承認」のような**人間の判断が必要な迂回**を実行させない。
  ユーザー本人が自分のターミナルで行うことで、判断の所在を人間側に残す。
