# 非エンジニアのためのAI駆動開発ガイド（2026年7月版）

> このガイドは「プログラミングはできないけれど、自分のアプリを作って公開したい」人のために書かれています。読み終わる頃には、AIに開発を任せて、あなたのアイデアを本物のWebアプリとしてインターネットに公開する道筋が見えているはずです。

---

## 第0章 この資料について

### 誰のためのガイドか

プログラミング経験ゼロ、またはほぼゼロの人が対象です。ExcelやWebブラウザが使えて、説明を見ながらコピペでコマンドを入力できれば十分です。

### 読み終わるとできること

- AI駆動開発が「何であって何でないか」を人に説明できる（第1章）
- 自分のPCにAI開発環境一式をセットアップできる（第2章）
- 「作りたいものの説明」から始めて、実際に動くWebアプリをインターネットに公開できる（第3章）
- 事故（想定外の課金・データ消失・情報漏洩）を起こさない習慣が身についている（第4章）

### かかる費用の目安

| 項目 | 金額 | 備考 |
|---|---|---|
| Claude Pro | $20/月（約3,000円） | AIの利用料。これが本体 |
| GitHub | 無料 | コードの保管場所 |
| AWS | ほぼ0円〜数百円/月 | 本ガイドの構成なら小規模利用はほぼ無料枠内。**ただし課金アラート設定は必須**（第2章） |

### このガイドの構成

**理解する（第1章）→ 環境を作る（第2章）→ 実際に作って公開する（第3章）→ 習慣を身につける（第4章）→ 次のステップ（第5章）** の順に進みます。急ぐ人は第2章から始めて、詰まったら第1章に戻る読み方でも大丈夫です。

大事な方針をひとつだけ先に伝えます。**このガイドは選択肢を見せません。** 「AとBどちらでも良い」は初心者を一番詰まらせる罠なので、道具もサービスも構成も、すべて1本の「黄金ルート」に決め打ちしてあります。慣れてから自分の好みに変えれば良いのです。

## 第1章 理解編 — AI駆動開発とは何か

### 1-1. あなたはディレクター、AIは開発チーム

AI駆動開発とは、**人間が「何を作るか・それで良いか」を決め、AIが「どう作るか・実際に作る」を担当する**開発スタイルです。

映画作りに例えると、あなたは監督です。脚本の意図を伝え、撮影されたシーンを見て「OK」か「撮り直し」かを判断します。カメラの操作や照明の設定（＝プログラミング）は専門スタッフ（＝AI）の仕事です。監督がカメラを操作できる必要はありませんが、**「何を撮りたいか」を明確に語れない監督の映画は必ず失敗します**。このガイドで一番大事なスキルは、プログラミングではなく「作りたいものを言葉にすること」です。

### 1-2. なぜ今、非エンジニアでも作れるのか

2023〜2024年のAIは「聞けばコードの断片を教えてくれる」レベルでした。2026年現在のAI（このガイドでは Claude Code を使います）は**エージェント**になりました。エージェントとは、指示を受けたら自分でファイルを作り、コマンドを実行し、エラーを見て自分で直し、ブラウザで動作確認までして戻ってくるAIのことです。

つまり「コードを書く作業」だけでなく、「エラーと格闘する作業」「動作確認する作業」までAIが自走します。人間に残された仕事は、要件を伝えることと、結果を確認することです。これは非エンジニアでもできます。

### 1-3. 3つの言葉 — プロンプト・コンテキスト・ハーネス

AI駆動開発の世界で必ず出てくる3つの言葉を、職場の新人教育に例えて整理します。

| 言葉 | 例えると | 具体的には | 効き目 |
|---|---|---|---|
| **プロンプト** | 口頭での指示 | 「ログイン画面を作って。青基調で」 | その場限り。伝え方次第 |
| **コンテキスト** | 渡しておく資料 | プロジェクトの説明書（CLAUDE.md）、要件メモ | AIが「読んで」動く。ただし忘れることも |
| **ハーネス** | 職場の仕組み | 危険な操作を物理的にブロックする設定、自動テスト、チェック体制 | **機械的に強制される。破られない** |

覚えてほしいのはこの一点です：**「お願い」は破られることがあるが、「仕組み」は破られない。**

AIに「重要ファイルを消さないで」とお願い（プロンプト）しても、AIは確率的にしか従いません。しかし「消そうとしたら機械的にブロックする設定」（ハーネス）を入れれば、100%防げます。第3章でこの「仕組み」を最初に張ってから開発を始めます。ちなみに世界最先端の開発組織も、いま同じ結論に達しています（「AIが失敗したら、もっと頑張れと言うのではなく、環境側に何が欠けているかを直す」）。あなたがやることは最前線のやり方と同じです。

### 1-4. できること・できないこと（期待値の調整）

**現実的にできること：**

- アイデアを伝えたその日のうちに、動く試作品を触る
- 数日〜数週間で、家族・友人・同僚に使ってもらえるWebアプリを公開する
- 公開後も「この機能を足して」で継続的に育てる

**できない・やってはいけないこと：**

- **曖昧な依頼から正解を当てさせること。** 「いい感じの家計簿アプリ作って」では、AIは「AIが考えるいい感じ」を作ります。要件を言葉にするのはあなたの仕事です（第3章で型を用意しています）
- **完全放置。** 節目ごとの確認（この画面でOK？この動きでOK？）は必須です。確認を怠ると、間違った方向に高速で進みます
- **お金・個人情報・健康を扱う本格サービスをこのガイドだけで公開すること。** 決済、他人の個人情報を預かる機能、医療系などは、専門家のレビューなしに公開してはいけません。まずは自分や身内が使う道具から始めましょう

### 1-5. 登場する道具の全体図

第2章でセットアップする道具たちです。今は「そういう役割の道具がある」と分かれば十分です。

| 道具 | 役割 | 例えると |
|---|---|---|
| **Claude Pro** | AI利用の契約プラン | 開発チームの雇用契約 |
| **Claude Code** | 開発を実行するAIエージェント本体。黒い画面（ターミナル）で動く | 開発チームそのもの |
| **spec-kit** | 「要件定義→計画→実装」の進行台本を提供する道具 | 進行が上手なプロジェクトマネージャー |
| **GitHub** | コードの保管庫。変更履歴が全部残る | 巻き戻しできる書類金庫 |
| **AWS** | アプリを24時間動かしてくれる場所 | 店舗を出すテナント |
| **MCP** | AIと外部サービス（GitHubやブラウザ）をつなぐ接続規格 | AIに持たせる社員証・鍵 |
| **skills（スキル）** | AIに渡す「仕事のやり方マニュアル」 | 業務手順書 |
| **ハーネス** | 事故防止の仕組み一式（ブロック設定・自動チェック） | 安全柵とセンサー |

## 第2章 準備編 — 環境を作る（所要2〜3時間）

この章は一度やれば終わりです。上から順に、飛ばさずに進めてください。

### 準備チェックリスト

- [ ] 2-1. Claude Pro を契約した
- [ ] 2-2. ターミナルを開けるようになった
- [ ] 2-3. Claude Code をインストールしてログインした
- [ ] 2-4. Git・Node.js と GitHub アカウントを用意した
- [ ] 2-5. AWSアカウントを作り、**課金アラートを設定した**
- [ ] 2-6. uv と spec-kit をインストールした
- [ ] 2-7. MCPを2つ（GitHub・Playwright）登録した

### 2-1. Claude Pro を契約する

1. https://claude.ai でアカウントを作成
2. 設定から **Proプラン（$20/月）** にアップグレード

Proには Claude Code の利用が含まれます。なお、チャット（claude.ai）と Claude Code の利用量は同じ「予算」を消費します。残量は claude.ai の `Settings > Usage` でいつでも確認できます（詳しくは第4章）。本ガイドはPro前提で書いていますが、上位のMaxプラン（$100/月〜）なら利用制限はほぼ気にせず使えます。

### 2-2. ターミナル（黒い画面）を開く

ターミナルは「文字でPCに指示を出す画面」です。怖がる必要はありません。このガイドで入力するものはすべてコピペで済みます。

- **Windows**: スタートメニューで「PowerShell」を検索して開く
- **Mac**: Spotlight（⌘+Space）で「ターミナル」を検索して開く

### 2-3. Claude Code をインストールする

ターミナルに以下を貼り付けて Enter：

- **Mac の場合**: `curl -fsSL https://claude.ai/install.sh | bash`
- **Windows (PowerShell) の場合**: `irm https://claude.ai/install.ps1 | iex`

終わったらターミナルを一度閉じて開き直し、`claude` と入力して Enter。初回はブラウザが開いてログインを求められるので、2-1 のアカウントでログインします。Claude Code の画面（対話画面）が出れば成功です。`/exit` と入力すると終了できます。

> インストールでエラーが出たら：エラーメッセージを全部コピーして claude.ai のチャットに貼り、「Claude Codeのインストールで失敗しました。OSは〇〇です。どうすればいいですか」と聞いてください。**以後すべてのトラブルはこの方法で解決できます。** これがAI時代のトラブルシューティングです。

### 2-4. Git・Node.js と GitHub を用意する

**Git**（変更履歴を記録する道具）のインストール：

- **Windows**: https://git-scm.com/download/win からインストーラーをダウンロードして実行（設定は全部そのままでOK）
- **Mac**: ターミナルで `git --version` と入力。入っていなければ案内に従ってインストール

**Node.js**（作ったアプリを手元で動かすための土台。Playwright MCPの動作にも必要）のインストール：

1. https://nodejs.org から **LTS版**（推奨版）をダウンロードしてインストール（設定は全部そのままでOK）
2. ターミナルを開き直して `node --version` と入力し、数字が表示されれば成功

**GitHub**（コードの保管サービス）のアカウント作成：

1. https://github.com で Sign up（無料プランでOK）
2. ユーザー名は半角英数字で。アプリの公開URLなどに使われます
3. **2段階認証（2FA）を設定**する（Settings → Password and authentication）。コードの保管庫が乗っ取られると全部やられます

### 2-5. AWSアカウントを作る — 課金アラートまでが儀式

AWSはアプリを動かす場所です。このガイドの構成（Amplify Hosting + DynamoDB）は小規模利用ならほぼ無料枠に収まりますが、**「気づいたら課金されていた」を仕組みで防ぐのが鉄則**です。以下を全部やってください。

1. https://aws.amazon.com/jp/ でアカウント作成（クレジットカード必須）
2. **ルートユーザーのMFA（2段階認証）を設定**：AWSコンソール右上のアカウントメニュー → セキュリティ認証情報 → MFAデバイスの割り当て。スマホの認証アプリ（Google Authenticator等）でOK
3. **課金アラートを設定（最重要）**：コンソールで「Budgets」を検索 → 予算を作成 → テンプレート「月次コスト予算」→ 金額 **$5** → 通知先に自分のメールアドレス。これで想定外の課金が始まったら即メールが来ます
4. **請求画面の場所を覚える**：コンソールで「Billing」を検索。月に1回は眺める習慣を

> なぜ$5？ このガイドの構成で正常なら月$0〜1程度だからです。$5を超えるメールが来たら「何かがおかしい」の合図。第4章のトラブル対応を見てください。

### 2-6. uv と spec-kit をインストールする

**spec-kit** は、GitHub社が公開している「要件定義→計画→実装」の進行台本ツールです（第3章の主役）。その動作に **uv** という道具が必要なので、2つ続けてインストールします。

**uv のインストール：**

- **Mac**: `curl -LsSf https://astral.sh/uv/install.sh | sh`
- **Windows (PowerShell)**: `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`

ターミナルを開き直してから、**spec-kit のインストール：**

```
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
```

確認として `specify check` を実行し、エラーなく表示されれば成功です。

### 2-7. MCPを2つ登録する — AIに「鍵」を渡す

MCPは、Claude Code に外部サービスへのアクセス手段を与える接続規格です。このガイドで使うのは次の**2つだけ**です（増やせば増やすほど便利になる、は罠です。第4章参照）。

| MCP | AIができるようになること |
|---|---|
| **GitHub MCP** | GitHubの操作（コードの保存・履歴確認）を安全な公式ルートで行う |
| **Playwright MCP** | ブラウザを自分で操作して、作ったアプリの動作確認をする |

ターミナルで以下を1行ずつ実行：

```
claude mcp add --transport http github https://api.githubcopilot.com/mcp/
claude mcp add playwright -- npx -y @playwright/mcp@latest
```

登録後、`claude` を起動して `/mcp` と入力すると接続状態を確認できます。GitHub MCPは初回にブラウザでのOAuth認証（GitHubアカウントでの許可）を求められるので許可してください。

これで準備完了です。いよいよ作ります。

## 第3章 実践編 — 要件定義からリリースまでの黄金ルート

この章が本編です。あなたのアイデアが公開アプリになるまでを **8ステップ** で進めます。

### 黄金ルートの全体地図

```
Step 1  プロジェクトを開始する          （specify init）
Step 2  安全柵を張る                    （CLAUDE.md と hooks ＝ハーネス）
Step 3  憲法を決める                    （/speckit.constitution）
Step 4  要件を言葉にする                （/speckit.specify → /speckit.clarify）
Step 5  計画を立てさせて読む            （/speckit.plan → /speckit.tasks）
Step 6  作らせる・自分で触る            （/speckit.implement → 動作確認）
Step 7  インターネットに公開する        （GitHub → AWS Amplify）
Step 8  育てる                          （機能追加は Step 4 に戻る）
```

技術構成は次の1本に固定します。**選ばない・迷わない・変えない**（慣れるまでは）。

| 部品 | 決め打ち | 理由 |
|---|---|---|
| アプリの作り | Next.js（Webアプリの定番フレームワーク） | 情報量が世界最多＝AIが最も上手に書ける |
| データ保存 | Amazon DynamoDB | 使った分だけ課金で、小規模ならほぼ0円。消し忘れ事故が起きない |
| 公開場所 | AWS Amplify Hosting | GitHubにコードを置くだけで自動公開。CI/CDが最初から付いてくる |
| 自動チェック | GitHub Actions | コードを保存するたびにテストが自動で走る |

### Step 1. プロジェクトを開始する

ターミナルで、作業フォルダを作って spec-kit を起動します。`myapp` は好きな名前（半角英数字）に変えてください。

```
specify init myapp --ai claude
cd myapp
claude
```

これで「spec-kitの台本が組み込まれた状態」で Claude Code が起動します。

### Step 2. 安全柵を張る（ハーネス）— 作り始める前に必ず

AIに「気をつけてね」とお願いするのではなく、**機械的にブロックする仕組み**を先に入れます。5分で終わり、以後ずっとあなたを守ります。

**① CLAUDE.md（プロジェクトの説明書）を置く。** プロジェクトフォルダ直下に `CLAUDE.md` という名前のファイルを作り、以下を貼り付けます（Claude Code に「CLAUDE.mdをこの内容で作って」と貼り付けて頼んでもOK）：

```markdown
# このプロジェクトのルール

## プロジェクト概要
- Next.js + DynamoDB のWebアプリ。AWS Amplify Hosting で公開する
- 開発者（私）は非エンジニア。専門用語は使う前に一言説明すること

## 進め方
- 大きな変更の前には、何をするかを先に説明して私の確認を取ること
- 作業が一区切りしたら git commit すること（コミットメッセージは日本語）
- 完了報告には「何をどう確認したか」の証拠（テスト結果・スクリーンショット）を添えること

## 禁止事項（hooksでも機械的にブロック済み）
- git push --force、git reset --hard、rm -rf の実行
- .env ファイルの内容をチャットに表示すること
- 私の確認なしに外部サービスへの課金が発生する操作をすること
```

**② 危険コマンドをブロックする hooks を入れる。** Claude Code にそのまま次を貼り付けて依頼します：

```
.claude/settings.json に PreToolUse hook を設定してください。
Bashツールの実行前に .claude/hooks/block-danger.sh を通し、
コマンドに git push --force / git reset --hard / git clean /
rm -rf / DROP TABLE のいずれかが含まれていたら
「危険コマンドのため禁止（CLAUDE.md参照）」とstderrに出して exit 2 で
ブロックするシェルスクリプトを作成してください。
```

AIが自分を縛る柵を自分で作る、というのが面白いところですが、これが2026年の標準作法です。「お願い（CLAUDE.md）」と「強制（hooks）」の二段構えにする理由は第1章1-3のとおりです。

### Step 3. 憲法を決める（/speckit.constitution）

Claude Code の画面で `/speckit.constitution` と入力すると、プロジェクトの「憲法」（全工程でAIが守る大原則）作りが始まります。質問には自分の言葉で答えればOKですが、迷ったら次を貼り付けてください：

```
このプロジェクトの原則：
1. シンプル最優先。機能は最小限から始めて、動いてから増やす
2. 技術構成は Next.js + DynamoDB + AWS Amplify Hosting に固定。提案があっても変更しない
3. 認証（ログイン機能）は初版では作らない
4. 私は非エンジニアなので、すべての説明は専門用語を避けるか、用語には一言の説明を付ける
5. テストが通っていない状態で「完成」と報告しない
```

### Step 4. 要件を言葉にする（/speckit.specify → /speckit.clarify）

いよいよ要件定義です。`/speckit.specify` に続けて、作りたいものを説明します。

**書き方のコツは「What（何ができる）とWhy（誰が何のために）」だけを書き、How（技術のこと）は一切書かない**ことです。技術は憲法で固定済みなので、AIに任せます。

記入例（家庭菜園の記録アプリの場合）：

```
/speckit.specify 家庭菜園の記録アプリを作りたい。

【誰のため】家庭菜園をやっている私自身。スマホのブラウザから使う。
【何のため】「いつ・何を・どうしたか」を忘れて毎年同じ失敗をするのを防ぐ。
【できること】
- 野菜ごとに「植えた日・水やり・肥料・収穫」を記録できる
- 野菜ごとの記録を時系列で一覧できる
- 写真も一緒に残せる（あれば嬉しい、なくても可）
【できなくていいこと】
- 他人との共有機能、ログイン機能、通知機能
```

書き終えると、AIが仕様書を作ります。続けて `/speckit.clarify` を実行してください。AIが「曖昧な点」を質問形式で聞いてきます。**この質問に答える時間が、プロジェクト全体で最も価値のある時間です。** ここでの1分は、後の手戻り1時間を防ぎます。

### Step 5. 計画を立てさせて、読む（/speckit.plan → /speckit.tasks）

`/speckit.plan` で実装計画を作らせます。技術構成を念押しする一文を添えてください：

```
/speckit.plan 技術構成は憲法どおり Next.js（App Router）+ DynamoDB。
公開は AWS Amplify Hosting。ローカル開発時はDynamoDBの代わりに
ローカル用の仮データ保存でよい。
```

計画ができたら、**流し読みでいいので必ず目を通してください**。全部理解する必要はありません。見るのは2点だけです：「作ると言っている画面・機能は、あなたが頼んだものと一致しているか」「頼んでいない大きなもの（ログイン機能など）が勝手に入っていないか」。

問題なければ `/speckit.tasks` でタスク一覧に分解させます。

### Step 6. 作らせる・自分で触る（/speckit.implement）

`/speckit.implement` で実装が始まります。AIがファイルを作り、エラーを直し、テストを回します。数十分かかることもあります。途中で確認を求められたら答えてください。

実装が終わったら、**必ず自分の目と手で確認します**：

1. Claude Code に「開発サーバーを起動して」と頼む（`npm run dev` が実行されます）
2. ブラウザで `http://localhost:3000` を開く
3. **ユーザーとして全機能を触る**。記録を追加する、一覧を見る、変な操作（空欄のまま保存等）もわざとやってみる

さらに、AI自身にも確認させます：

```
Playwrightでブラウザを操作して、主要な機能（記録の追加・一覧表示）が
実際に動くことを確認し、スクリーンショット付きで報告してください。
```

直したいところは、遠慮なく・具体的に伝えます。「なんか違う」ではなく「一覧画面の日付を『7月9日』形式にして。今は『2026-07-09』になっている」のように。

### Step 7. インターネットに公開する（GitHub → AWS Amplify）

自分のPCの中だけで動いていたアプリを、URLを持つ本物のWebアプリにします。

**① GitHubに保存する。** Claude Code に頼みます：

```
このプロジェクトをGitHubの新しいプライベートリポジトリとして
push してください。リポジトリ名は myapp で。
```

**② 自動チェック（CI）を仕込む。** 続けて頼みます：

```
GitHub Actions のワークフローを作ってください。
main ブランチに push されるたびに、lint とテストが自動実行される
最小構成（.github/workflows/ci.yml）でお願いします。
```

これで「コードを保存するたびに自動で検査が走る」状態になります。これがCIです。

**③ AWS Amplify Hosting につなぐ。** ここはAWSの画面での操作です：

1. AWSコンソールで「Amplify」を検索して開く
2. 「新しいアプリを作成」→「GitHub」を選択 → 認証してリポジトリ `myapp` と `main` ブランチを選択
3. ビルド設定はNext.jsが自動検出されるのでそのまま「保存してデプロイ」
4. 数分待つと `https://main.xxxx.amplifyapp.com` のようなURLが発行されます

**④ DynamoDB（本番のデータ保存）をつなぐ。** 最後の配線はAIに設計させ、あなたはコンソールをポチポチする係です：

```
Amplify Hosting 上の本番環境から DynamoDB を使えるようにしたい。
必要な作業（テーブル作成、Amplifyのコンピュートロールへの権限付与、
環境変数の設定）を、AWSコンソールでの手順として1つずつ案内してください。
私が画面を操作するので、1手順ずつ確認しながら進めてください。
```

これで完成です。発行されたURLをスマホで開いて、あなたのアプリが動いていることを確かめてください。**以後、コードをGitHubにpushするたびに、検査→公開が全自動で走ります**（これがCI/CDです）。

### Step 8. 育てる — 公開してからが本番

機能を足したくなったら、**Step 4 に戻って同じ台本を繰り返すだけ**です：

```
/speckit.specify 既存の菜園記録アプリに機能追加。
収穫した野菜の写真をカレンダー形式で見られる画面が欲しい。…
```

→ clarify → plan → tasks → implement → 自分で触る → push（自動で公開）。

このループを回すたびに、あなたの「要件を言葉にする力」とAIへの指示の精度が上がっていきます。それがAI駆動開発の上達です。

## 第4章 これやっとけば良い集

3カテゴリ、全19項目のチェックリストです。**まずカテゴリA（事故防止）だけは全部**やってください。BとCは開発に慣れながら1つずつ増やせば大丈夫です。

### カテゴリA：事故防止 — お金・データ・秘密を守る

- [ ] **A-1. AWS課金アラートを設定した（第2章2-5）。** 想定外の課金は非エンジニア最大の事故です。$5の予算アラートが「何かおかしい」を知らせる煙探知機になります。メールが来たら、AWSコンソールのBillingで何に課金されているかを確認し、分からなければ請求画面のスクリーンショットをClaudeに見せて相談してください。

- [ ] **A-2. 「確認をスキップする起動オプション」を使わない。** Claude Code には確認なしで全操作を許可する起動方法（`--dangerously-skip-permissions`）がありますが、名前のとおり危険です。ネット記事で「これで楽になる」と紹介されていても、安全柵を外して高速道路を走る行為だと思ってください。確認が面倒になってきたら、安全なコマンドだけを個別に許可リストへ登録するのが正しい楽の仕方です（`/permissions` で設定できます。Claudeに「このコマンドを許可リストに入れて」と頼めばOK）。

- [ ] **A-3. 危険コマンドブロックのhooksを入れた（第3章Step 2）。** 「消して困るものを消せない仕組み」は、新しいプロジェクトを作るたびに最初に入れます。お願い（CLAUDE.md）と強制（hooks)の二段構えが基本です。

- [ ] **A-4. 秘密情報をチャット・CLAUDE.md・GitHubに書かない。** APIキー・パスワード・接続文字列は `.env` というファイルに置き、GitHubには上げない（Claudeが自動で除外設定します。「.envがgitignoreされているか確認して」と聞けば確認できます）。公開後に必要な秘密情報はAmplifyの環境変数設定に入れます。**一度GitHubに上げてしまった秘密情報は、削除しても履歴に残るため「漏れた」と同じです。** その場合は当該キーを無効化・再発行してください。

- [ ] **A-5. MCPは公式のものだけ、必要最小限を入れる。** MCPはAIに渡す「鍵」です。個人が作った出所不明のMCPには、悪意ある仕掛けが入っている事例が報告されています。ベンダー公式（GitHub社、Microsoft、AWS等）か公式レジストリのものだけを入れ、使っていないMCPは削除しましょう。増やすほど便利になるどころか、AIの動きはむしろ鈍くなります。

- [ ] **A-6. こまめに「コミットして」と言う。** git commit は「セーブポイント」です。何かが動いた節目ごとにコミットしておけば、AIが何かを壊しても「さっきのコミットまで戻して」の一言で復旧できます。CLAUDE.mdに書いてあっても、大事な節目では自分からも言う習慣を。

- [ ] **A-7. 本物の個人情報をテストに使わない。** 動作確認用のデータは架空の名前・住所・メールで。「テスト用の架空データを10件作って」と頼めば作ってくれます。家族や友人の実名を試しに入れたものが、スクリーンショットやGitHub経由で漏れるのが典型事故です。

### カテゴリB：効率 — AIの働きを最大化する

- [ ] **B-1. 話題を変えるときは `/clear`。** Claude Codeは会話の全履歴を毎回読み直しています。別のタスクに移るときに `/clear` で履歴をリセットすると、動きが速く・正確に・利用量も節約になります。「1つの会話には1つの仕事」が原則です。

- [ ] **B-2. 大きな変更は「計画→実行」の2段階で。** いきなり作らせず、まず計画を立てさせて読んでから実行させます。Claude Codeにはこのための機能（プランモード：Shift+Tabで切替）が組み込まれています。第3章の spec-kit の台本は、これを工程として強制する仕組みでもあります。

- [ ] **B-3. 同じ指示を2回したらCLAUDE.mdに書く。** 「日本語でコメントして」を2回言ったら、それはCLAUDE.md行きです。逆にCLAUDE.mdを長くしすぎると全体が読み飛ばされます。目安は100〜150行。「この行を消したらAIはミスするか？」と自問して、Noなら消します。

- [ ] **B-4. 残量を見てから働く。** claude.ai の `Settings > Usage` に利用量の残りとリセット時刻が表示されます。長時間作業する日は最初に確認を。上限に達しても、5時間ごとに回復します。急ぎの日のために「使用量クレジット」（上限後の従量課金オプション）を有効化しておく手もあります。

- [ ] **B-5. claude.ai側の相談は「プロジェクト」に資料を置いて。** アイデア出しや要件の壁打ちをclaude.aiのチャットでやる場合、資料を毎回貼り付けるのではなく、Projects機能のKnowledgeに登録しましょう。登録済み資料はキャッシュされ、利用量をほぼ消費せずに何度でも参照されます。

- [ ] **B-6. 音声入力を使う。** 話す方がタイピングの3倍速く、自然と説明が詳しくなるので、AIへの指示の質が上がります。要件を伝える場面（第3章Step 4）で特に有効です。

### カテゴリC：品質 — 「動いた」を「ちゃんと動く」にする

- [ ] **C-1. AIに自分の目で確認させる。** 「作りました」を信用せず、「Playwrightでブラウザを操作して、実際に動くことを確認してから報告して」と頼みます。AIは検証手段を与えられると、自分で不具合を見つけて直すループに入ります。これが品質を上げる最大のコツです。

- [ ] **C-2. 証拠付きの報告をルールにする。** 「完了しました」ではなく「テスト12件が全部通りました。スクリーンショットはこれです」と報告させます（第3章のCLAUDE.md雛形に組み込み済み）。証拠のない完了報告は完了ではありません。

- [ ] **C-3. テストが緑になってから次へ。** 「この機能のテストを書いて、通るまで直して」を口癖に。テストは、後からAIが別の場所を触ったときに「以前の機能を壊していないか」を自動で見張ってくれる番人になります。

- [ ] **C-4. 同じ失敗が2回続いたら、押し方を変える。** 3回目の「もう一回やって」は時間の無駄です。選択肢は3つ：①要件に戻る（そもそも伝え方が曖昧だった）②`/clear`して新しい会話でやり直す（会話が混乱している）③問題を小さく割る（一度に頼みすぎた）。

- [ ] **C-5. 1回のお願いは1つのこと。** 「AとBとCを直して」より、A→確認→B→確認→C。特に公開後のアプリでは、1機能ずつ確認して進む方が結局速いです。

- [ ] **C-6. うまくいった型は書き戻す。** 良い指示の仕方や決まりごとが見つかったら、CLAUDE.mdや憲法に追記します。あなたのプロジェクトは使うほど賢くなっていきます。これは最先端の開発組織がやっている「ハーネス改善ループ」の一人版です。

## 第5章 発展編 — 次のステップ

黄金ルートを2〜3周した人向けの寄り道案内です。

### 5-1. ログイン機能を足したくなったら

自分専用から「他人に使ってもらう」段階に進むと認証（ログイン）が必要になります。AWSにはAmplifyと相性の良い認証サービス（Amazon Cognito）があり、Claudeに「Amplify + Cognito でメールアドレス認証を追加したい。計画から」と頼めば黄金ルートの延長で作れます。ただし認証は事故ると影響が大きい領域なので、`/speckit.specify` からの正規ルートで、テストまで含めて作らせてください。

### 5-2. 要件定義の質を上げる `/grill-me`

要件の曖昧さを潰す作業を、AIの側から質問攻めしてもらうスキルがあります。世界的に有名なエンジニアMatt Pocock氏の公開スキル集に入っている `/grill-me` で、導入は1コマンドです：

```
npx skills@latest add mattpocock/skills
```

導入後、`/grill-me 〇〇なアプリを作りたい` と話しかけると、AIが計画の穴を1問ずつ質問して埋めてくれます。spec-kitの `/speckit.clarify` の強化版として、大きめの機能を作る前に使うのがおすすめです（実は、このガイド自体も `/grill-me` で要件を詰めてから書かれています）。

### 5-3. さらに広い世界の歩き方

スキルやテンプレートの公開リポジトリは無数にあります。代表格は次のとおりですが、**「全部入り」に手を出すのは慣れてから**にしてください。部品を1つずつ理解して足すのが、結局いちばん速い道です。

| リポジトリ | 何か | 向き合い方 |
|---|---|---|
| [mattpocock/skills](https://github.com/mattpocock/skills) | 小さく合成可能な仕事術スキル約20個 | `/grill-me` から。初心者に最適 |
| [github/spec-kit](https://github.com/github/spec-kit) | このガイドの背骨。仕様駆動開発の台本 | 導入済み。公式ドキュメントを時々見る |
| [anthropics/skills](https://github.com/anthropics/skills) | Anthropic公式スキル集（文書作成等） | 資料作りにも使える |
| [affaan-m/everything-claude-code](https://github.com/affaan-m/everything-claude-code) | 232スキルの巨大詰め合わせ | 眺めて学ぶ場所。丸ごと入れない |
| [VoltAgent/awesome-agent-skills](https://github.com/VoltAgent/awesome-agent-skills) | ベンダー公式スキルの索引 | 使うサービスの公式スキルを逆引き |

### 5-4. その先へ — チーム開発とマルチエージェント

プロの現場では、複数のAIエージェントに役割（調査係・実装係・監査係）を与えて分業させ、人間は要件の正本と受け入れ判断だけを握る、という開発の「型」作りが進んでいます。合言葉は「人間が舵を取り、エージェントが実行する」。本ガイドで身につけた「要件を言葉にする→仕組みで縛る→証拠で確認する」は、そのままその世界の入場券です。1人で黄金ルートを回せるようになったあなたは、もう入り口に立っています。

## 付録A 用語ミニ辞典

| 用語 | 意味 |
|---|---|
| ターミナル | 文字でPCに指示を出す画面。コピペで使えれば十分 |
| リポジトリ | プロジェクト一式の保管単位。GitHub上の「フォルダ」と思えばOK |
| コミット | 変更履歴のセーブポイント |
| プッシュ（push） | 手元の変更をGitHubに送ること |
| デプロイ | アプリを公開環境に配置すること |
| CI/CD | push のたびに検査（CI）と公開（CD）が自動で走る仕組み |
| ローカル | 自分のPCの中のこと（⇔ 本番＝公開環境） |
| ビルド | コードを実行可能な形に変換する処理 |
| フレームワーク | アプリの土台となる骨組み（本ガイドでは Next.js） |
| トークン | AIが読み書きする文章量の単位。利用量の元 |
| コンテキスト | AIが「今覚えていられる」作業記憶。長い会話ほど圧迫される |
| MCP | AIと外部サービスをつなぐ接続規格（AIに渡す鍵） |
| スキル | AIに渡す仕事のやり方マニュアル（SKILL.mdファイル） |
| hooks | 特定の操作を機械的にブロック・実行する強制の仕組み |
| ハーネス | AIが確実に仕事をやり遂げるための環境一式（柵とセンサー） |

## 付録B 詰まったときのトラブルシューティング

**原則：エラーは読まずに、コピーしてAIに貼る。** エラーメッセージ全文＋「何をしようとしていたか」をClaude（Code でも claude.ai でも）に貼れば、大半は解決します。以下は頻出パターンです。

| 症状 | 対処 |
|---|---|
| 利用上限に達した | 5時間ごとに回復。`Settings > Usage` でリセット時刻を確認。待てない場合は使用量クレジット（第4章B-4） |
| AIの様子がおかしい・堂々巡り | `/clear` で会話をリセットし、要件から言い直す（第4章C-4） |
| AIが何かを壊した | 「直近の正常なコミットまで戻して」。こまめなコミット（A-6）が効く場面 |
| Amplifyのデプロイが失敗 | Amplifyコンソールのビルドログを全文コピーしてClaudeに貼り「デプロイが失敗しました」 |
| ローカルでは動くのに本番で動かない | 「本番だけで起きる問題です。環境変数とDynamoDBの権限を疑って調査して」と伝える |
| AWSから$5アラートのメールが来た | Billing画面で課金元サービスを確認→スクリーンショットをClaudeに見せて「原因と止め方を教えて」 |
| GitHub MCPの認証が切れた | Claude Code内で `/mcp` → 該当サーバーの再認証 |
