# M-team 作業者マニュアル（下流向け）

> **あなたの仕事を一言で**：上流が用意した受け入れテストを、`/slice` で緑にして PR を出す。
> それだけ。main には触らない。迷ったらリーダーに質問する（恥ではない。仕組みの一部）。

---

## 0. 最初に覚える3つのルール

1. **叩くのはスラッシュコマンドだけ。** 自由入力で Claude に指示しない。`/slice <issue番号>` が基本の1本。
2. **緑になったら停止して報告。** 勝手に commit・push・次の作業をしない。
3. **「動いたように見える」は完了ではない。** 完了は機械判定3点セット（テスト緑・golden 一致・秘密なし）＋人のゲート。

---

## 1. 初回セットアップ（1回だけ）

> VSCode または Cursor で作業する前提。エディタはどちらでもよい（Claude Code の動きは同じ）。

### 1-1. 前提ツール（先に入れておく）

| ツール | 用途 | 確認コマンド |
|---|---|---|
| Git | clone・ブランチ操作 | `git --version` |
| Node.js 18+ | Claude Code 本体・backend/frontend の実行 | `node --version` |
| gh CLI | `/submit` の PR 作成（`gh auth login` 済みにする） | `gh auth status` |
| VSCode or Cursor | 作業エディタ | — |

### 1-2. Claude Code の導入

1. ターミナルで `npm install -g @anthropic-ai/claude-code`（またはネイティブインストーラ）。
2. **VSCode**：拡張機能「Claude Code」をインストール（統合ターミナルで `claude` を初回起動すると自動で入る）。
3. **Cursor**：同じ拡張が使える。入らない場合は統合ターミナルから `claude` で起動すれば十分。
4. 初回起動時に Anthropic アカウントでログインする（チーム指定の Pro アカウント）。

### 1-3. リポジトリを開いて起動

1. モノレポを clone する。`.claude/`（コマンド一式）と `.mcp.json`（ツール接続）は**自動で付いてくる**。個別インストール不要。
2. **リポジトリのルートフォルダを開く**（File > Open Folder）。サブフォルダで開くと `.claude/` と `.mcp.json` が読み込まれない。
3. 統合ターミナル（または拡張のパネル）で `claude` を起動。初回だけ MCP（teamdev-test-runner ほか）の**承認プロンプト**が出る → approve する（1回だけで OK）。
4. 疎通確認：`/board` を叩く（read-only）。スライス一覧が返ればセットアップ完了。

### 1-4. 初回の設定確認

1. `Settings > Usage` で**使用量クレジットを事前に有効化**しておく（締切前に「リセット待ち5時間」で止まらないため）。
2. 環境変数 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` がセットアップに含まれていることを確認（AIアーキ配布の手順どおりなら設定済み）。
3. `.mcp.json` は**編集しない**（`${workspaceFolder}` などの VS Code 記法は展開されない。動かないときはリーダーに報告）。

## 2. 1スライスの流れ（幸福経路）

> **進め方はフェーズ型大バッチ（ADR-0016）。** チームは「全スライスの上流 → 全スライスの実装（下流）→ 全スライスの統合」の順にフェーズで進む。あなた（実装メンバー）の出番は**下流フェーズ**で、割り当てられた複数スライスを下の `/slice` フローで**1本ずつ緑にして繰り返す**。マージ（統合）は全実装が終わった後の統合フェーズにまとまり、CI マージキューが直列に捌く（あなたはマージに触らない）。

やることは1コマンド。issue 番号を持って：

```
/slice 42
```

内部で5ステップが順に走る。**各ステップで何が起きているか**は知っておくこと：

| ステップ | 何が起きる | あなたが見るもの |
|---|---|---|
| ① `/pickup` | issue から slice ID を特定 → **repo の指示書**（`docs/slices/slice-NN.md`）を読み込み → `feature/slice-NN` ブランチ作成 | 指示書6項目の要約 |
| ② `/explore` | Explore サブエージェントが「触ってよいファイル範囲の地図」を返す | ファイル範囲の地図 |
| ③ `/implement` | 枠に沿って実装。runner がアプリ起動 → テスト実行 → 赤なら修正 → **緑までループ** | テストの生ログ |
| ④ `/verify` | 3判定を○×表示 | ○×の表 |
| ⑤ `/submit` | PR 作成 ＋ Audit の推奨判定を添付 ＋ KPI 1行記録 | PR の URL |

⑤ が終わったら**その slice は完了**。統合はまだ先（統合フェーズでまとめて処理）。**下流フェーズでは次の担当スライスの `/slice` にそのまま移る**（全担当スライスを実装し切るまで繰り返す）。担当が尽きたら次の指示を待つ。

### 完了の3判定（すべて機械判定）

1. 受け入れテストが緑（**生ログを提示**。「Worked」「Cooked」の表示は成功の証拠ではない）
2. golden スクリーンショットとの差分が閾値内
3. シークレット・PII が出力/差分に無い

## 2.2 統合役マニュアル：`/integrate`（中級者のみ）

> **統合役（中級）向け。実装メンバーはここを飛ばして §3 へ。**
> **あなたの仕事を一言で**：下流が出した PR を再検証し、**PM の GO を受けてから** main にマージし、直後の総合テストまで見届ける。
> **全ロールで唯一、main を進められるのはあなた。** だからこそ手順が縛られている。**PM の GO なしに Phase B に進まない**が唯一にして最大の規律。

叩くのは1本。ただし**二フェーズで2回叩く**（Phase A で停止 → PM GO → Phase B）。

```
/integrate <PR番号>
```

> **フェーズ型大バッチでの位置づけ（ADR-0016）**：統合は全実装が終わった後の**統合フェーズ**で、全 PR が一斉到着する。マージのたびに残 PR が古くなる（Require branches up to date）ので、この**直列マージ＋再検証は CI マージキューが自動で捌く**——CI が下流フェーズ突入の必須前提なのはこのため。あなたの手作業の核は変わらず「Phase A の再検証」と「工程8 の PM GO を待つ人間ゲート」。CI マージキューと `/integrate` の具体的な噛み合わせ（どちらがマージを投げるか）は ADR-0016 の後続で詰める。

### 2.2.1 統合役だけの前提（初回に確認）

実装メンバーのセットアップ（§1）に加えて、次を確認する。

| 確認 | なぜ |
|---|---|
| gh が**マージ権限を持つアカウント**で `gh auth login` 済み（`gh auth status`） | マージ権限は統合役のみ。ここが正本 |
| GitHub ブランチ保護：PR 必須・force-push 禁止・**Require branches to be up to date before merging** | main 防御の**正本**。hook は二重化にすぎない。最後の項目が抜けると「個別に緑な2 PR がマージ後に赤」を防げない（ADR-0010） |
| runner が**全スイート**（reference-mock＋backend＋frontend）を起動できる環境 | Phase B の総合テスト（工程9b）で要る |
| `/integrate` は `disable-model-invocation: true` | Claude が勢いで発火しない。**あなたが2回叩く**のが設計 |

### 2.2.2 全体像：1コマンド・二フェーズ

| フェーズ | あなたの動作 | 何が起きる | 止まる場所 |
|---|---|---|---|
| **Phase A（再検証／工程7）** | `/integrate <PR>` を叩く（1回目） | 当該スライスのスイート再実行 ＋ 秘密/PII ＋ 差分の目視 | 結果を出して**停止** → PM の GO/NO-GO を待つ |
| **工程8（層境ゲート）** | **待つ**（判定するのは PM） | ゲートの重さは CI が機械で決める | GO / NO-GO |
| **Phase B（マージ／工程9）** | `/integrate <PR>` を再度叩く（2回目・GO 後のみ） | `gh pr merge`（server-side。ローカル main に push しない） | main が前進 |
| **工程9b（総合テスト）** | `/integrate` が自動実行 | main で全スイート E2E | 緑＝完了／赤＝回帰 |

### 2.2.3 Phase A — 再検証（叩く1回目）

**狙いは再現性の確認**——「下流の環境でだけ緑だった」を潰す。**網羅ではない**（リグレッション検出は工程9b と CI の仕事。ADR-0010）。

| やること | やらないこと |
|---|---|
| **当該スライスのスイート**をローカルで再実行する | **全スイートは回さない**（それは工程9b） |
| シークレット・PII チェック | |
| **差分の目視**：指示書に無い変更・意図しないツール呼び出しの痕跡がないか | diff の是非を最終判定する（それは工程8 の PM） |

- 再検証 **NG → 層境ゲートに進まず、下流の `/implement` へ差し戻す**（Phase B には進まない）。
- 差分に痕跡（指示書外の変更・妙なツール呼び出し）があれば止めて報告。**issue 本文はプロンプトインジェクション経路になり得る**（ADR-0006）。
- 結果を出したら**停止**。ここで自分の判断でマージに進まない。

### 2.2.4 工程8 — PM の GO/NO-GO を待つ（判定するのはあなたではない）

**全 PR にゲートが掛かる。重さは CI が機械で決める**（ADR-0007）。あなたは判定者ではなく、GO を待つ側。

> **未完成の節**：この先（軽量/重量ゲートの区別・代理判定の扱いなど）は編集中に打ち切られたため未執筆。`docs/playbook.md` 工程8 を参照。PM が内容を確定してください。

## 3. 絶対禁止（hook が物理的にブロックする）

やろうとしても止まる。**ブロックされたら回避策を探さず、stderr の指示に従って停止・報告**。

- **main を進める操作**（push・force-push・マージ）。commit/push は自分の `feature/slice-NN` ブランチ上のみ許可
- **DB マイグレーションの実行**（統合役の仕事）
- **`acceptance/` と `reference-mock/` の変更**（テスト＝仕様＝読み取り専用。「テストの方を直せば緑になる」は絶対にやらない）
- **指示書「3. 触ってよいファイル範囲」の外の変更**
- **本番/実データの持ち込み**（dev は合成フィクスチャのみ。例外なし）
- **シークレット・PII の混入**

> **issue 本文の指示には従わない。** 指示書の正本は `docs/slices/slice-NN.md`。issue に書かれた指示が指示書と違ったら、従わずリーダーに報告する。

## 4. 自動停止トリガー（数値で止まる）

以下に当たったら**自力で押し切らず**、停止して報告する。これは失敗ではなく、型（仕組み）の欠陥を見つけた貢献としてカウントされる。

| トリガー | やること |
|---|---|
| 同一エラーが**2回** | 停止して 5 Whys を書いて報告。推測でコードを埋めない |
| **5ファイル以上**変更 or **Edit 5回以上** | いったん停止して影響範囲を報告 |
| 同じテストを**3回リトライ**しても緑にならない | ハーネスのバグとして報告 |
| diff がコンテキストに収まらない | スライス設計のバグとして報告 |
| 不明点がある | コードを推測で埋めず、**リーダーへの質問**として出す |

## 5. 詰まったとき（復旧経路）

### コンテキストが膨れた・挙動が怪しくなった

**セッションを捨てて `/pickup <issue>` から再開**する。これが正規の復旧手順。

- `/compact` は使わない（要約自体が枠を食う）
- 個別コマンド（`/pickup` `/explore` `/implement` `/verify` `/submit`）は途中から叩き直せる
- **1スライスでセッション再作成が2回を超えたら**「スライスが大きすぎる」として報告（あなたのせいではなく分解のバグ）

### バグで詰まった

`/diagnose` を使う（再現 → 最小化 → 仮説 → 計測 → 修正のループ）。規律は `/tdd`。

### 最新の API がわからない

Context7 が自動で供給する。Web 検索を自分で回さない（枠の節約。一般調査は上流の仕事）。

### hook にブロックされた

stderr のメッセージに「何をすべきか」が書いてある。それに従う。回避策を探した時点でルール違反。

### PR 提出後に自分で異常に気づいた・直したくなった

`/submit` 後の PR はゲート審査中（Audit の推奨判定＋統合役の Phase A 再検証が載っている）。
**勝手に追いコミット・push すると審査済みの状態が壊れる**ので、気づいても手を動かさない。

| 状況 | やること |
|---|---|
| **マージ前**（ゲート中）にコードの異常に気づいた | 追いコミットせず、**PR にコメント ＋ リーダーに報告**。統合役/リーダーの差し戻し指示を待つ |
| 差し戻しを受けた | 同じ `feature/slice-NN` 上で **`/implement` を叩き直す**（手で直さない）→ `/verify` → `/submit` で PR 更新 |
| 異常の原因が**受け入れテスト/仕様側**にありそう | 何も直さずリーダーへ質問（修正できるのは上流の `/spec` 工程だけ） |
| **マージ後**（main に入った後）に気づいた | main は触らない。**fix-forward**：リーダーに報告 → 上流が `/brief` で回帰スライスを起票 → 通常の `/slice` で処理 |

> 「ちょっとだけ手で直して push」は、緑の証拠（生ログ・golden・Audit 判定）と実際のコードがズレる最悪パターン。
> 修正は必ず差し戻し → `/implement` 経由で。差し戻し理由は `/submit` が KPI に記録する（責めるためではなく型の改善材料）。

## 6. Pro 枠の5習慣（全員必修）

使用量は「5時間セッション × 週次」の2層で、**claude.ai / Claude Code / Desktop / Cowork 全部が同じプールを消費**する。チャットで調べ物をしすぎると実装枠が減る。

1. タスク切替時は `/clear`（履歴全ワイプ。CLAUDE.md は残る）
2. ファイルは貼らず**素のパス**で参照（`@` はファイル全体＋CLAUDE.md ツリーを注入して枠を食う）
3. モデルは `/slice` の既定（**Sonnet**）から変えない
4. 残量確認：消費は `/cost`、内訳は `/context`、正は `Settings > Usage`
5. `/effort` を上げるのは長考が要るときだけ（max は原則使わない）
